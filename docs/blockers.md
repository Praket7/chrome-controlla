# Blockers and external dependencies

## Phase 0

No Phase 0 blocker. The local Rust installation was discovered at `~/.cargo/bin`; it was not initially on the login shell PATH. Build evidence below invokes Cargo by its absolute path.

## Later qualification

Client live qualification, paid app entitlements, test accounts, and platform-specific interference observation have not been attempted. These are unverified future gates, not Phase 0 passes or confirmed blockers. Record an exact missing prerequisite only when its phase is reached.

## Phase 1 boundary

- The Phase 1 CLI does not ship a daemon or end-user browser route. Doctor can probe a configured local PID and loopback authenticated health service; only mock-service fixtures are available here, so no live service/transport result is claimed. Windows process liveness remains explicitly unknown.
- The target-bound npm archive/install check has local macOS arm64 evidence and hosted CI run `37465119376` passed the package checks on Ubuntu, macOS, and Windows for commit `8dbf51d`. This verifies those host-built CI artifacts only; it does not imply a published release or qualify other OS/CPU combinations. Every release cell needs its own host build.
- Registry provider availability is fixture-backed. Catalog and dispatch share registry-owned revisions and policy reevaluation, but these fixtures do not establish a running direct CDP connection or extension bridge.

## Phase 2 implementation boundary

- The browser crate has persistent CDP target/frame graphs, stale target references bound to random per-connection instance IDs, per-target scheduling (default active-tab ceiling 4), shared-document mutation locks, and direct-CDP owned-target create/close. A dedicated provider launches an explicit Chrome executable into a new profile (0700 on Unix), waits for its loopback DevTools endpoint, and returns a live recovery handle if cleanup lacks an independent current in-tab observer. Unit fixtures cover fake launch success/failure, cancellation, cleanup retry, and preservation when unrelated page targets remain. The explicit local Google Chrome 154.0.8037.98 headless smoke passed: isolated profile launch, CDP target creation, `Runtime.evaluate` returned `document.visibilityState = visible`, the test-owned target closed, and the isolated process/profile were removed. No user profile was used or altered. Real headed desktop launch remains unverified; shutdown never closes a headed Chrome window automatically.
- `extensions/chrome-controlla/` is an unpacked MV3 extension for explicitly checked tabs. The Rust `SharedExtensionProvider` issues one-session loopback pairing credentials, binds the session to a unique instance and exact numeric Chrome tab IDs, routes target-scoped commands, and reevaluates grant/membership before dispatch. Direct-CDP `Browser.*`/`Target.*` routes are rejected for shared sessions. Rust fixtures exercise the bridge protocol; they do not run the extension in Chrome or qualify debugger consent, browser versions, background lifetime, or platform behavior.
- Account and document revisions in `TargetRef` are supplied by the caller; this crate has no authoritative application identity observer. They prove equality against supplied revisions only. Focus, cursor, clipboard, and foreground/background effects have no native observer and remain unqualified.
- Production owned-target receipts are sealed to the provider create result; test-only ledger setup is private, and callback-based registry cleanup is crate-private. CDP target metadata cannot prove an in-tab user edit, so `release_owned_session` closes nothing unless a trusted independent observer verifies the current in-tab state. No such observer ships here; owned tabs remain retryable and shutdown returns the live process/profile in a recovery handle. Crash reconciliation reports surviving owned targets but does not automatically close them.
- Phase 2 source/provider fixture checks and the dedicated headless Chrome smoke are local only. No live extension installation or debugger-consent result, headed Chrome run, live browser client, or independent native focus/cursor/clipboard observer is claimed. Platform focus/cursor/clipboard and foreground/background cells remain unqualified. Shutdown checks the current page-target list before closing headless Chrome, but this is a snapshot and cannot rule out a page opened immediately before `Browser.close`; close errors and timeouts preserve the process/profile for retry. The Phase 2 live qualification gate remains open pending an independent cleanup observer and browser-side qualification.

## Phase 3 boundary

- The runtime now has a local SQLite journal and lifecycle state API, but this repository still has no MCP jobs tool, dispatch handler, or bridge/CDP mutation execution route. Accepted work is not automatically scheduled from a client request; reconnect is represented only by reading the durable operation record.
- `recover_uncertain` is an explicit recovery hook and must run only after recovering a prior runtime's database; it marks in-flight records unknown rather than retrying. The journal cannot establish whether a remote Chrome effect happened, and no API promotes unknown because this phase has no independent observer.
- Job reads and state changes require the exact principal and session stored at admission. `record_dispatch` returns an explicit acquisition result; only its first successful claim may send the correlated request. Delivery remains unknown after an unconfirmed claim, including a crash before transport send.
- Each job has a persisted deadline (60 seconds by default and the maximum in this phase). Expiry before dispatch yields `failed` with `deadline_error=deadline_exceeded` and `delivery=not_sent`; expiry/recovery after dispatch sets status to `unknown` while preserving acknowledged `sent` delivery or unacknowledged `unknown` delivery. A caller wait timeout does not change job state.
- Local fixtures do not qualify a real JavaScript Promise, the exact 12-second case, navigation during evaluation, process-kill injection at every storage/dispatch boundary, or CDP/extension route parity. No exactly-once browser effect or live MCP acceptance is claimed.

## Phase 4 boundary

- `crates/controlla-browser/src/input.rs` resolves supported semantic locators fail-closed and dispatches guarded CDP text, click, and drag operations through revision-bound references. Isolated Chrome fixtures cover ordinary input/caret readback, stale-value refusal, marked masked/event-dependent and contenteditable refusals, password non-disclosure, overlay interception, DOM drag bounds, and simulated IME composition. Composition does not qualify the OS IME candidate UI or app-specific controls. Canvas drag returns unsupported unless an app-specific outcome verifier is available; click/drag without a declared observable predicate return unsupported.
- Account/document checks compare caller-supplied revision values. No authoritative application identity or user-edit observer is implemented; page content does not expand authority.
- The mock CDP fixture injects a navigation change and observes the pending fill withheld. Fill also compares the live page value inside the same synchronous evaluation that writes it; insert and each key event recheck target value and focus immediately before the individual CDP send. These checks narrow the race window only: CDP processing, page event handlers, and server-side effects are not atomic. The earlier 2773 us mock timing is not a bound on Chrome processing or a guarantee against intervening changes.
- Strict-background uses page/CDP text/file routes and fails with `NeedsForeground` for mouse/native routes. Per-session text insertion never uses the OS clipboard. File artifacts use opaque session/principal-scoped handles (10 MiB per file, 16 files/50 MiB per session); on Unix, guarded CDP file-input selection uses private 0700/0600 temporary paths and reports `Selected` only. The local MCP fixture covers `artifact_register` and guarded `file_select`; failed deletion stays tracked in the cleanup receipt for retry; registry drop attempts best-effort cleanup. One isolated Chrome check confirms unchanged frontmost app, cursor, and pasteboard change count. The native snapshot is macOS-only; app acceptance/persistence, Windows/Linux qualification, and repeated live interference remain unverified.

## Phase 5 boundary

- The runtime exposes local MCP stdio session, observe/extract, shared-tab pairing/observation, and artifact registration/file-selection routes. These paths have mocked-CDP/loopback bridge fixture coverage; the unpacked Controlla extension is loaded in Chrome, but a live pairing/dispatch was not completed and no external MCP client acceptance is claimed. The shared extension route uses its declared `chrome.debugger` permission and does not require Chrome DevTools remote debugging to be enabled. Direct CDP requires `COMPTROL_ALLOW_DIRECT_CDP=1` and an explicitly configured loopback IP WebSocket; permissioned auto-connect requires its own opt-in and Chrome's remote-debugging consent. There is no remote listener or synthetic authentication.
- Observation includes selected-node partial accessibility and bounded PNG crop routes. AX selects one DOM node and does not fetch the entire tree; crop pixel area is rejected before CDP capture when it exceeds the requested output budget. Target references are revalidated against the session's selected target set and live browser graph.
- Extraction supports caller-declared sections, optional verified expansion controls, and single-use resumable cursors bounded by target/revision/spec, expiry, and retained-state limits. Stable IDs are section-scoped under deterministic per-section record/byte shares and a global deadline. Each section still needs its own matching identity marker, independently authoritative expected count, and container-scoped terminal marker at scroll end on two no-new-ID observations before contributing `complete`. Trimming or missing fields/clipping/truncation prevents aggregate `complete`; wrong-account 404 remains mock/policy-tested.
- Page scripts cap DOM node traversal, record materialization, text and serialized page-result bytes before returning to Rust. Rust also enforces the exact serialized `Observation`/`ExtractionResult` size including metadata; if the metadata envelope cannot fit, the call errors. This is a node/byte/text bound, not a wall-time guarantee for native selector or page `innerText` evaluation.
- Phase 5 policy and isolated Chrome fixtures cover recycled records, hidden/blocked expansion, AX, crop, cursor resume/stale rejection, and bounded extraction. The prior 42-row timing comparison remains a single synthetic diagnostic, not a performance claim. Representative application loading, account markers, accessibility trees, canvas visuals, and terminal signals remain unqualified; no external MCP client acceptance is claimed. Artifact file selection is direct-CDP only and reports browser selection, not application acceptance or persistence; shared-extension input/extraction and artifact output/download are not implemented.

## Phase 6 boundary

- Workflow MCP admission starts a durable job and returns its operation ID; `workflow_status` retrieves persisted revisions and latest checkpoints under a 60-second deadline. Browser operations are claimed/countable before dispatch and timeouts retain unknown delivery. Client disconnect does not cancel an accepted job, and there is no workflow-cancel tool. At process startup, accepted jobs are failed as not sent and running jobs become unknown while preserving their latest checkpoint; Chrome sessions are not rehydrated and interrupted jobs are not resumed.
- The stdio server takes an exclusive OS file lock on its state directory before opening or recovering the journal and holds it for the server lifetime. Concurrent MCP clients must use distinct directories, for example `CONTROLLA_STATE_DIR="$HOME/.chrome-controlla/client-a" controlla mcp` and `CONTROLLA_STATE_DIR="$HOME/.chrome-controlla/client-b" controlla mcp`; PowerShell can set `$env:CONTROLLA_STATE_DIR` to a distinct path before each server launch. A duplicate owner exits before journal recovery with an actionable error. Per-client generated configuration examples will be added with Phase 9 client integration.
- The pinned in-process `rquickjs 0.14.0` worker is only enabled by `CHROME_CONTROLLA_ENABLE_TRUSTED_SCRIPTS=1`. Its fresh context has no module loader, file/network/process globals, or raw CDP; the only async host call is an observe broker that rechecks authority per call. Interrupt, memory, stack, source, output, deadline, and operation limits are tested. These API limits are not an OS/process security boundary; untrusted and production scripts stay blocked pending process isolation, hard RSS/CPU controls, host cancellation behavior, and platform qualification. `node:vm` is not used as a security boundary.
- Current scripts can only perform bounded observation; mutation programs and effect-aware splitting are not implemented. Receipts include counts and target/revision identity but workflow-generated artifacts are not implemented and the artifact list is empty. Dependency-scoped invalidation and benchmark comparison remain open build-plan items.
