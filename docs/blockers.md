## Phase 8 app workflow gates

Planning-only MCP tools now build a revision-bound Slides text request and a 10-slide editable deck candidate, compile a five-page Canva design candidate, and validate a supplied CapCut licensed-media/timeline recipe. Slides/Canva preconditions are explicitly marked non-authoritative; the Slides compiler never emits delete requests and the Canva sync candidate is advisory. `capcut_web_plan` remains explicitly unsupported until a live versioned control map and independent verifier exist. These offline planners are not app routes: no vendor app is connected and none of these tools edits a document or uploads media.

The current MCP server exposes generic session, observation/extraction, accessibility/crop, artifact registration, file selection, and a fixture-verified guarded `shared_input` fill/click route. It rechecks click geometry immediately before dispatch and attempts a release after every attempted press, but a page may still change in the small validation/dispatch gap and a failed release can leave pointer state uncertain. In either case the operation returns an error; reobserve before further input. The route verifies DOM state and root-frame identity only; it does not expose app-specific mutations or runtime-controlled app-save verification. Google Slides planning now includes its exact POST URL, JSON content type and required OAuth scope, but this is request construction only: no credential injection, network dispatch, app write, or readback is present. Generic file selection is not app acceptance or persistence evidence. A dedicated Chrome test profile and test-account sign-in were approved, but no app-specific execution route is implemented and no app write was attempted. Representative test documents/media and a supported route are still prerequisites for live qualification; authentication alone does not supply the missing route.

Current vendor documentation confirms that Google Slides `batchUpdate` supports revision-checked writes via `writeControl.requiredRevisionId` ([Google Slides batchUpdate](https://developers.google.com/workspace/slides/api/reference/rest/v1/presentations/batchUpdate)). Canva's Design Editing API can read/edit page elements, but its sessions expire after one minute and `sync` applies snapshot edits to the live design before refreshing the snapshot; locked pages are read-only ([Canva Design Editing API](https://www.canva.dev/docs/apps/design-editing/)). No official general CapCut Web timeline API was confirmed in the searches; third-party draft/CLI tooling is not treated as an authorized web-app route.

## Phase 3 boundary

- The runtime now has a local SQLite journal and lifecycle state API, but this repository still has no MCP jobs tool, dispatch handler, or bridge/CDP mutation execution route. Accepted work is not automatically scheduled from a client request; reconnect is represented only by reading the durable operation record.
- `recover_uncertain` is an explicit recovery hook and must run only after recovering a prior runtime's database; it marks in-flight records unknown rather than retrying. The journal cannot establish whether a remote Chrome effect happened, and no API promotes unknown because this phase has no independent observer.
- Job reads and state changes require the exact principal and session stored at admission. `record_dispatch` returns an explicit acquisition result; only its first successful claim may send the correlated request. Delivery remains unknown after an unconfirmed claim, including a crash before transport send.
- Each job has a persisted deadline (60 seconds by default and the maximum in this phase). Expiry before dispatch yields `failed` with `deadline_error=deadline_exceeded` and `delivery=not_sent`; expiry/recovery after dispatch sets status to `unknown` while preserving acknowledged `sent` delivery or unacknowledged `unknown` delivery. A caller wait timeout does not change job state.
- Local fixtures do not qualify a real JavaScript Promise, the exact 12-second case, navigation during evaluation, process-kill injection at every storage/dispatch boundary, or CDP/extension route parity. No exactly-once browser effect or live MCP acceptance is claimed.

## Phase 6 boundary

- Workflow MCP admission starts a durable job and returns its operation ID; `workflow_status` retrieves persisted revisions and latest checkpoints under a 60-second deadline. Browser operations are claimed/countable before dispatch and timeouts retain unknown delivery. Client disconnect does not cancel an accepted job, and there is no workflow-cancel tool. At process startup, accepted and running/not-sent jobs fail as not sent; jobs past the dispatch claim become unknown while preserving observed delivery and the latest checkpoint. Chrome sessions are not rehydrated and interrupted jobs are not resumed.
- The stdio server takes an exclusive OS file lock on its state directory before opening or recovering the journal and holds it for the server lifetime. Concurrent MCP clients must use distinct directories, for example `CONTROLLA_STATE_DIR="$HOME/.chrome-controlla/client-a" controlla mcp` and `CONTROLLA_STATE_DIR="$HOME/.chrome-controlla/client-b" controlla mcp`; PowerShell can set `$env:CONTROLLA_STATE_DIR` to a distinct path before each server launch. A duplicate owner exits before journal recovery with an actionable error. Phase 9 generates isolated client examples; they still need validation in real clients.
- The pinned in-process `rquickjs 0.14.0` worker is only enabled by `CHROME_CONTROLLA_ENABLE_TRUSTED_SCRIPTS=1`. Its fresh context has no module loader, file/network/process globals, or raw CDP; the only async host call is an observe broker that rechecks authority per call. Loop interrupts, never-settling-Promise deadlines, memory, stack, source, output, and operation limits are tested. A script timeout drops the active QuickJS future; these API limits are not an OS/process security boundary. Untrusted and production scripts stay blocked pending process isolation, hard RSS/CPU controls, disconnect-cancellation semantics, and platform qualification. `node:vm` is not used as a security boundary.
- Trusted local scripts can perform bounded observation and return one inline artifact using {kind:"artifact",filename,media_type,bytes:[...]}. The runtime rejects unknown fields, unsafe basenames, non-allowlisted media types, empty or over-12-KiB bytes, and out-of-range byte values. Bytes and SHA-256 are stored in the durable operation receipt with operation/principal/session identity and retrieved through `workflow_status`; no filesystem path or download handle is created. The in-process worker remains unqualified as an OS security boundary, so scripts stay default-off and limited to trusted local use. Dependency-scoped invalidation and effect-aware splitting exist as deterministic planning rules; the Phase 6 fixture comparison reports operation/recovery counts only. Arbitrary mutation integration, file-backed/download artifacts, measured browser overhead, and wall-clock profiling remain open.
