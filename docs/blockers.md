# Blockers and external dependencies

## Phase 0

No Phase 0 blocker. The local Rust installation was discovered at `~/.cargo/bin`; it was not initially on the login shell PATH. Build evidence below invokes Cargo by its absolute path.

## Later qualification

Client live qualification, paid app entitlements, test accounts, and platform-specific interference observation have not been attempted. These are unverified future gates, not Phase 0 passes or confirmed blockers. Record an exact missing prerequisite only when its phase is reached.

## Phase 1 boundary

- The Phase 1 CLI does not ship a daemon or end-user browser route. Doctor can probe a configured local PID and loopback authenticated health service; only mock-service fixtures are available here, so no live service/transport result is claimed. Windows process liveness remains explicitly unknown.
- The target-bound npm archive/install check has local macOS arm64 evidence and hosted CI run `37465119376` passed the package checks on Ubuntu, macOS, and Windows for commit `8dbf51d`. This verifies those host-built CI artifacts only; it does not imply a published release or qualify other OS/CPU combinations. Every release cell needs its own host build.
- Registry provider availability is fixture-backed. Catalog and dispatch share registry-owned revisions and policy reevaluation, but these fixtures do not establish a running direct CDP connection or extension bridge.

## Phase 2 implementation boundary

- The browser crate has persistent CDP target/frame graphs, stale target references bound to random per-connection instance IDs, per-target scheduling (default active-tab ceiling 4), shared-document mutation locks, and direct-CDP owned-target create/close. A dedicated provider launches an explicit Chrome executable into a new profile (0700 on Unix), waits for its loopback DevTools endpoint, and returns a live recovery handle if cleanup lacks an independent current in-tab observer. Unit fixtures cover fake launch success/failure, cancellation, cleanup retry, and preservation when unrelated page targets remain. The explicit local Google Chrome 154.0.8037.98 headless smoke passed: isolated profile launch, CDP target creation, `Runtime.evaluate` returned `document.visibilityState = visible`, the test-owned target closed, and the isolated process/profile were removed. No user profile was used or altered. Real headed desktop launch remains unverified; shutdown never closes a headed Chrome window automatically.
- `extensions/chrome-controlla/` is an unpacked MV3 extension for explicitly checked tabs. The Rust `SharedExtensionProvider` issues one-session loopback pairing credentials, binds the session to a unique instance and exact numeric Chrome tab IDs, routes target-scoped commands, and reevaluates grant/membership before dispatch. Direct-CDP `Browser.*`/`Target.*` routes are rejected for shared sessions. Rust fixtures exercise the bridge protocol; they do not run the extension in Chrome or qualify debugger consent, browser versions, background lifetime, or platform behavior.
- Account and document revisions in `TargetRef` are supplied by the caller; this crate has no authoritative application identity observer. They prove equality against supplied revisions only. Focus, cursor, clipboard, and foreground/background effects have no native observer and remain unqualified.
- Production owned-target receipts are sealed to the provider create result; test-only ledger setup is private, and callback-based registry cleanup is crate-private. CDP target metadata cannot prove an in-tab user edit, so `release_owned_session` closes nothing unless a trusted independent observer verifies the current in-tab state. No such observer ships here; owned tabs remain retryable and shutdown returns the live process/profile in a recovery handle. Crash reconciliation reports surviving owned targets but does not automatically close them.
- Phase 2 source/provider fixture checks and the dedicated headless Chrome smoke are local only. No live extension installation or debugger-consent result, headed Chrome run, live browser client, or independent native focus/cursor/clipboard observer is claimed. Platform focus/cursor/clipboard and foreground/background cells remain unqualified. Shutdown checks the current page-target list before closing headless Chrome, but this is a snapshot and cannot rule out a page opened immediately before `Browser.close`; close errors and timeouts preserve the process/profile for retry. The Phase 2 live qualification gate remains open pending an independent cleanup observer and browser-side qualification.

## Phase 3 boundary

- The runtime now has a local SQLite journal and lifecycle state API, but this repository still has no MCP jobs tool, dispatch handler, or bridge/CDP mutation execution route. Accepted work is not automatically scheduled from a client request; reconnect is represented only by reading the durable operation record.
- `recover_uncertain` is an explicit recovery hook and must run only after recovering a prior runtime's database; it marks in-flight records unknown rather than retrying. The journal cannot establish whether a remote Chrome effect happened, and no API promotes unknown because this phase has no independent observer.
- Job reads and state changes require the exact principal and session stored at admission. `record_dispatch` returns an explicit acquisition result; only its first successful claim may send the correlated request. Delivery remains unknown after an unconfirmed claim, including a crash before transport send.
- Each job has a persisted deadline (60 seconds by default and the maximum in this phase). Expiry before dispatch yields `failed` with `deadline_error=deadline_exceeded` and `delivery=not_sent`; expiry/recovery after dispatch sets status to `unknown` while preserving acknowledged `sent` delivery or unacknowledged `unknown` delivery. A caller wait timeout does not change job state.
- Local fixtures do not qualify a real JavaScript Promise, the exact 12-second case, navigation during evaluation, process-kill injection at every storage/dispatch boundary, or CDP/extension route parity. No exactly-once browser effect or live MCP acceptance is claimed.

## Phase 4 boundary

- `crates/controlla-browser/src/input.rs` resolves supported semantic locators fail-closed and dispatches guarded CDP text, click, and drag operations through revision-bound references. An ignored installed Chrome 154 headless fixture verifies ordinary text-input fill/insert/sequential ASCII values and caret readback. Mock websocket fixtures verify click/drag envelopes and declared predicates; real overlay interception, DOM drag effects, masked/contenteditable/IME/event-dependent fields, and canvas drag behavior remain unqualified. Click/drag without a declared observable predicate return unsupported.
- Account/document checks compare caller-supplied revision values. No authoritative application identity or user-edit observer is implemented; page content does not expand authority.
- The mock CDP fixture injects a navigation change after target revalidation but before the subsequent text write and observes the write withheld; its probe-to-fill message-arrival interval was 2773 us in one recorded run. This does not measure Chrome's internal processing or close the post-check race window. Page event handlers and remote effects remain non-atomic.
- Strict-background uses only page/CDP text routes and fails with `NeedsForeground` for mouse/native routes; it has no system clipboard operation. The implementation does not call OS focus/cursor/clipboard APIs, but unchanged native state is not independently observed. B24/B25 remain unqualified pending native observers.
