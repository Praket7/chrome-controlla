# Native desktop fallback

The direct `act` route and `workflow` route share one bounded desktop action contract. When a platform capability is enabled, a request must carry a registered screenshot revision and a declared visible outcome. Before dispatch, Controlla rechecks the live session, exact provider-owned tab, document identity, visual revision and age, viewport, foreground mode, focused Chrome window, and platform support. The native action is followed immediately by a read-only verification step.

On macOS, the experimental adapter uses ScriptingBridge addressed to the exact Chrome process that launched the paired native messaging host. Its Swift helper currently runs without a stable signed app identity, so `browser action=describe` reports `helper_identity_supported: false` and native input is refused. The reported `helper_permission_identity` is diagnostic only; do not grant Accessibility, Input Monitoring, or Automation permissions to `swift-frontend` or an ephemeral helper. Native fallback stays unavailable until Controlla packages a stable signed helper identity. Extension-based browser actions do not need these macOS permissions. If a future stable helper is added, its permission probes must continue to run in the same process that receives those permissions. The selected tab ID and source URL must match fresh evidence; unknown delivery must never be replayed.

The current macOS fallback does not support native actions: the Swift helper lacks a stable signed app identity, so the server refuses dispatch and `browser action=describe` reports it unavailable. Do not grant macOS permissions to the ephemeral helper. If a stable helper is packaged later, pointer movement, scrolling, and bounded non-submitting keys may be considered; coordinate clicks, drags, all text entry, and navigation remain refused because native visual evidence cannot safely classify those targets or payloads. Use extension-backed semantic actions for clicks, drags, typing, and navigation; those paths use fresh page references and the order-confirmation gate. Chrome tab groups and browser windows remain managed through the extension-backed `browser` tab API. Windows and Linux native input remain unavailable until platform-specific permission and desktop tests pass.

## Verification boundary

Local tests cover envelope bounds, opaque native-text refusal, coordinate click/drag refusal, native-host PID binding, ownership checks, direct-route schema, workflow gating, helper scope, helper-identity reporting, and refusal/unknown receipts. The Swift helper compiles and its read-only probe runs when Swift is installed. Native actions are not advertised or dispatched while the helper lacks a stable signed identity; enabling them requires a future packaged helper and live qualification. Ordinary extension-based page actions do not require Accessibility permission.
