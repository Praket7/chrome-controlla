# Phase 9 B35 blind app-scenario evaluation

## Method and scope

A fresh agent evaluated the five scenario names supplied for B35 against the current `docs/MASTER_GUIDE.md` (local preview `master-2026-10-06-v3`) and the rebuilt packaged local MCP server's `tools/list` output. The server was started from `packages/chrome-controlla/dist/bin/controlla-core mcp` with a newly created temporary `CONTROLLA_STATE_DIR`, using JSONL MCP initialize protocol `2025-11-25`, an `notifications/initialized` notification, then `tools/list`. The packaged server identified itself as `controlla-runtime` version `0.1.0`.

No browser or design app was connected or inspected. No source files or other documentation were read for this evaluation. The exact original scenario prompts were not available; the scenario descriptions below restate only the names and requested task types provided to the evaluator. The scoring rule was: PASS when a novice should choose a supported route or clearly refuse/request a blocker without inventing capability; PARTIAL/FAIL otherwise.

## Results

| Scenario description | Outcome | Evidence and smallest gap |
|---|---|---|
| Actual Google Slides edit request | **PASS** | Guide §13 says `slides_plan_text_edit` is planning only, makes no app connection or mutation, and that app mutations should be reported unsupported until a route and evidence gates are qualified. Packaged `slides_plan_text_edit` schema requires `principal`, `account_id`, `presentation_id`, `required_revision_id`, and `operation`; its description says it builds a request “without dispatching it” and OAuth, live checks, readback, and persistence verification are not connected. Smallest gap: no edit execution or verification route. |
| Canva preflight/sync | **PASS** | Guide §13 describes `canva_sync_preflight` as validation of a caller-supplied snapshot, says it does not connect to Canva, notes `sync` can write, and says not to call `sync` in this preview. The packaged schema requires `principal`, `account_id`, `design_id`, `page_id`, `revision`, `page_type`, `locked`, and `opened_at_ms`; its description says it never opens a Canva session or calls sync. Smallest gap: no independently verified session freshness/page lock or sync/edit/persistence route. |
| CapCut edit request | **PASS** | Guide §13 says there is no CapCut edit/execute/verify route and instructs reporting an unsupported requested step until qualified. Packaged `capcut_web_plan` schema requires an `operation` string; its description says operations remain unsupported until a live versioned control map and independent verifier are qualified. Smallest gap: no qualified controls or independent verifier. |
| Native file picker/upload proof | **PASS** | Guide §1 and §6 distinguish `artifact_register` plus `file_select` from a native picker: file selection uses the page's existing `<input type="file">`, does not open/control an OS picker, and proves only selected name/size, not app acceptance or saving; arbitrary host paths are not accepted. §12 separates selection, transfer, app acceptance, and persistence. Packaged `artifact_register` schema takes session-scoped bounded bytes and a filename. The rebuilt `file_select` schema requires `session_id`, complete `target_ref`, `locator`, `artifact_handle`, and `account_marker`; `locator` is a `$ref` to `FileSelectLocator`, whose `anyOf` is a closed union of `RoleNameLocator`, `LabelLocator`, `PlaceholderLocator`, `TextLocator`, `TestIdLocator`, `AltTextLocator`, `HrefContainsLocator`, `SelectorLocator`, and `BackendNodeIdLocator`. Each locator object disallows extra properties and requires its specific key(s); for example, `SelectorLocator` requires `selector`. §6 says identify the actual file input, usually with a CSS selector, and selection does not click submit or verify transfer, app acceptance, or persistence. The tool description says success proves Chrome selection/readback, not app acceptance. Smallest gap: no native picker route or app upload/save proof. |
| User interference/stale target | **PASS** | Guide §10 says to yield, describe the change, preserve human edits, and reobserve/replan remaining work. §14 maps `user_interference` to yielding/preserving/replanning and `stale_target` to refreshing the handle. The packaged `shared_input` schema requires an explicit `chrome_tab_id`, selector, action, exact `expected_value`, and value; its description limits freshness/readback claims. Direct CDP observation tools use the complete revision-bound `target_ref` schema. Smallest gap: none identified in the documented response behavior; this outcome depends on following the guide's stop/reobserve instructions. |

## Limits

These outcomes assess whether the documented guide and rebuilt packaged tool descriptions/schema direct a novice toward a supported route or a clear refusal. They do not establish real-client acceptance, live app behavior, actual edits, upload acceptance, persistence, or app-specific verification. The guide itself identifies representative app behavior and qualification as open; this evaluation made no live connections.
