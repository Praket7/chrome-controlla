# Phase 11 public read-only pilot

`node bench/runners/phase11-public-readonly-pilot.mjs --repetitions=1` runs isolated Codex CLI tasks using the same model and installed Chrome executable. The configured adapters are Controlla, pinned Playwright MCP 0.0.83, Chrome DevTools MCP 1.10.1, agent-browser 0.39.1, locally installed Browser Use MCP 0.13.11, and Stagehand 4.1.0. The Browser Use server source file byte-matches checkout commit `c75e8476e26d18b7617643bc2ae082fae8eae431`. Stagehand is built from exact tag/commit `@browserbasehq/stagehand@4.1.0` / `cd7b230778cf92269e4cb90e80d97f5113781c51`; the runner checks the built stdio facade hash before recording results. Set `CONTROLLA_STAGEHAND_SERVER` or pass `--stagehand-server` when the pinned source is installed outside the home-directory default. Each adapter must read the current title and first English paragraph at `https://example.com/` and close its isolated browser. Controlla uses one private headless `browser action=task` call; Stagehand uses one `run` call. Stagehand receives a run-specific `TMPDIR`/`TMP`/`TEMP` so its temporary Chrome profile stays inside the disposable task workspace. Cleanup requires its close request, absence of the Stagehand server/temporary Chrome processes, and no newly created `stagehand-chrome-*` profile. Process inventory uses PowerShell on Windows and `ps` on macOS/Linux. A separate Node HTTPS request fetches the public page after each agent run. The runner reports two independent correctness checks: `browser_outcome_matches_reference` searches successful browser tool results for both exact reference values, and `final_answer_matches_reference` checks the agent's final JSON. Overall verification requires both, along with observed navigation, read, cleanup, and no unrelated actions. Each run gets a new temporary workspace and browser state, which are removed after completion.

The runner records **Codex process-spawn-to** browser outcome, independent verification, and final answer separately. Its clock starts immediately before `codex exec` is spawned; the CLI JSON stream does not expose when the prompt is internally dispatched, so these measurements are not exact user prompt-SEND latency. Browser-outcome time ends when the structured browser read returns; independent-verifier time includes the separate HTTPS reference fetch and exact comparison. The runner also records browser tool calls, prompt hash, Chrome version, model, Controlla binary digest, failed tool errors, bounded per-call arguments and task receipts, answer, cleanup evidence, and verifier evidence. Exact internal model round trips are unavailable in the CLI stream. Input and output token totals are reported separately. The adapter prompts have matching semantics but tool-specific instructions, so this is a pilot, not a controlled universal comparison. Browser Use uses direct `browser_navigate`, `browser_get_html`, and `browser_close_all` tools under a unique headless Chrome profile and downloads directory; it does not invoke Browser Use’s autonomous task agent. Its cleanup verifier requires a successful navigation acknowledgement followed by `Closed 1 sessions` with no reported errors. Browser Use is included in the latest five-adapter five-pair live result below. Its initial `uvx --from git+...` launch failed inside Codex before MCP initialization; a child-process diagnostic reproduced Git requirement resolution failure, so the pilot now uses the installed executable. The runner now accepts `--browser-use-executable` or `CONTROLLA_BROWSER_USE_EXECUTABLE`, then verifies package version 0.13.11 and the MCP server file hash before recording Browser Use results. The report labels `c75e8476e26d18b7617643bc2ae082fae8eae431` as the pinned source commit, not a runtime-attested package-tree identity; only the package version and `browser_use/mcp/server.py` hash are checked. The earlier smoke in `reports/phase11-browser-use-local-executable-smoke-2026-10-14.json` predates runtime identity labeling and is retained as historical evidence. The identity-guarded smoke in `reports/phase11-browser-use-identity-guard-smoke-2026-10-14.json` passed exact browser-result and final-answer checks in three calls, including verified `Closed 1 sessions` cleanup; process spawn to browser evidence was 8.900 s and to final answer was 13.012 s. It records the verified package version and MCP server file hash while explicitly stating that the full package Git commit is not attested. This one run is not a comparative latency estimate.

The first successful pair on 2026-10-14 used Chrome 155.0.8059.40 and `gpt-6-luna`:

### Runtime cost telemetry correction

The current candidate corrects V3 route receipts: physical Chrome DevTools Protocol requests are reported as `cdp_commands`; deterministic task size is reported separately as `logical_task_steps`; page-tool invocations use `external_page_tool_calls`. Earlier `browser_operations` values mixed these unlike units and should not be compared. A post-rebuild isolated headless Example.com read completed and released its private session: the task receipt measured 213 ms and 2 logical steps, while the enclosing launch/read/release operation recorded 50 CDP request/response cycles and 1.425 s. This is one diagnostic sample, not a latency benchmark. Aggregate counts still do not identify which CDP methods account for the total.

The independent command-count trace attributes most avoidable traffic to repeated structural snapshots during route selection and learning, plus repeated readiness polling. Those are follow-up optimization opportunities; the current telemetry correction makes their cost visible without mislabeling physical CDP requests as logical browser actions.

The current runner also records the first browser tool start and leaves exact internal model round trips as `null` because Codex's JSON stream does not expose them.

This is one simple, cold, public read-only task. It does not run the 19 live-site classes, repeated cold/warm cohorts, user profile, external competitor matrix, or statistical success and latency analysis. It cannot satisfy `check:release --claim`, and no superiority claim follows from it. The production comparison still needs an independent browser-state verifier and real reset for each task class, executable adapters for the other competitors, matched prompts and model settings, repeated runs, and a complete environment record.
